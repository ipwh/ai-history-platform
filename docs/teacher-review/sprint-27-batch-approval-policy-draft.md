# 批次覆核政策草案（待歷史科主任及產品負責人決定）

**狀態**：`POLICY DECISION REQUIRED` — **未獲批准，未執行，不得據此改動任何題目狀態。**
**版本**：草案 v0.1（2026-10-23，Sprint 27）
**適用範圍**：`school-paper` 1,372 題（舊版本批准、現行內容已改動）

---

## 1. 為甚麼需要這份政策

3,205 道已發布題目中，1,372 道只有**舊 revision** 的 `approved` 覆核。Sprint 27 已用
指紋比對證實：這 1,372 題的**現行內容與批准時的內容全部不同**（0 題相同），
其中 1,281 題同時帶有 `explanation_rewritten` 旗標（解釋重寫計劃），91 題的改動未能以此解釋。

另一方面，這些題目當初的批准是**擁有者批次發布**（`reviewer_role = admin`，
理由「擁有者指示：本 session 上載的校內題庫題目一律覆核通過並發布」，1,877 列），
**不是**歷史科教師逐題裁決。

因此需要一個明確的決定：**舊版批准在甚麼條件下可以視為覆蓋現行版本**，或一律需要重新確認。

## 2. 三個可選方案（各有代價，請選一個）

### 方案 1：全部重新確認（最嚴格）

- 1,372 題全部由教師按現行版本逐題確認。
- 成本：每人每日處理量有限；以每題 1–2 分鐘計，1,372 題約需 23–46 小時（單人）。
- 優點：無政策爭議，證據最強。
- 缺點：在完成前 `review-provenance` gate 保持 FAIL。

### 方案 2：限定範圍的批次覆核（建議採用，需明確定義）

只對「改動僅限解釋文字、且解釋改寫已在教師清單內」的題目發出一個**有限定範圍**的批次決定，
其餘（91 題及其他）逐題處理。

- 優點：可在一至兩個工作天內把缺口由 1,372 降至 91（若教師接受）。
- 風險：**解釋是學生看到的內容**，重寫後的解釋可能改變教學重點、因果說明或難度；
  「只改解釋」不等於「不影響學習」。採用此方案必須接受這個風險，並配合抽樣核查。
- 必要條件（缺一不可）：
  1. 範圍明確：只包括 `origin = 'school-paper'` **且** 帶有
     `question_content_flags.flag = 'explanation_rewritten'`、`state = 'open'` 的題目；
  2. 排除條件：`teacher_confirmation_required = 1`、`status != 'published'`、
     或指紋顯示題幹／選項／答案曾改動的題目**一律排除**；
  3. 責任人：具名的歷史科主任（email 記錄在 `--owner-email`）；
  4. 依據：本文件 + 抽樣核查紀錄（建議每 20 題抽 1 題，共約 64 題）；
  5. 決策期限：完成抽樣核查後方可執行批次；
  6. 政策版本：`batch-approval-policy/v0.1`（寫入每個理由字串）。

### 方案 3：不處理，接受 gate 維持 FAIL

- 平台照現狀運作（題目仍是 published、學生可用），但 release gate 保持 `NOT READY`，
  且不得部署。
- 這在技術上可行，但等於接受「44.9% 的已發布題目沒有現行版本證據」長期存在。

## 3. 執行機制（若採用方案 2，仍受以下限制）

- **只可使用既有機制**：`npm run approve:questions`（擁有者授權批次覆核）會**逐題寫入**
  `question_reviews`（含 reviewer、revision、fingerprint、理由）。這是**記錄**，不是偽造：
  它如實記錄「誰在何時、依哪份政策、對哪一版作出決定」。
- **不可**直接用 SQL 改 `status` 或插入紀錄；
- **不可**把批次決定寫成「教師逐題裁決」；
- 理由字串必須包含政策版本與範圍，例如：
  `批次政策 batch-approval-policy/v0.1（主任姓名）：解釋重寫計劃後之現行版本；範圍 school-paper + explanation_rewritten；抽樣核查 64 題完成於 2026-10-2X`
- 執行前後必須各跑一次 `npm run audit:approval-drift` 存證。
